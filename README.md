# Segue — Backend

**매장에 원하던 제품이 없을 때, 고객의 마지막 의도를 구조화해 다음 행동 하나를 제안하는 Client Advisor용 상담 보조 서비스.**

## 어떤 문제를 푸나

고객이 온라인에서 담아둔 제품이 방문한 매장에 없을 때, 지금의 응대는 대개 "비슷한 거 보여드릴까요?" 아니면 "재고 확인해 볼게요"로 끝난다. 고객이 **애초에 왜 그 제품을 골랐는지**는 반영되지 않는다.

정확한 디자인 때문인지, 소재 질감을 직접 보고 싶은 건지, 오늘 당장 필요한 건지에 따라 답은 완전히 달라져야 한다. Segue는 그 "왜"를 CA가 짧은 대화로 끌어내고, 구조화된 조건을 재고·제품 속성과 대조해 **다음 행동 하나만** 제안한다.

---

## 핵심 설계 — AI는 결정하지 않는다

AI에게 "어떤 제품을 추천할까"를 물으면 답은 나오지만, **그 근거는 답을 정한 뒤에 지어낸 것**이다. 같은 고객에게 매번 다른 답이 나올 수도 있고, 왜 그 제품인지 CA가 고객 앞에서 설명할 수도 없다.

그래서 역할을 나눴다.

```
고객 발화(자연어)
   │
   ▼
AI ①  의도 구조화          ── 고객의 말을 정해진 어휘의 조건으로 옮긴다
   │
   ▼
   조건이 충분한가? ──── 부족 ──▶ AI ②  보충 질문 1회 ──┐
   │ 충분                                              │
   ▼                                                   │
규칙 엔진  제품 속성 · 재고 · 조건 대조  ◀───────────────┘
   │
   ▼
결과 4가지 중 하나로 확정
   │
   ▼
AI ③  확정된 근거로 설명문 생성
   │
   ▼
Last Intent Card
```

**AI 호출 세 번 어디에도 "무엇을 추천할지" 묻는 단계가 없다.** 마지막 AI는 이미 확정된 결과를 문장으로 옮길 뿐이라 없는 사실을 지어낼 수 없고, 브랜드 금지어와 조건 환각은 백엔드에서 한 번 더 검증한다.

판단 우선순위는 코드에 고정되어 있다.

> ① 필수 조건 → ② 구매 시급성 → ③ 실물 확인 필요 → ④ 확보 경로(대기·타 매장) → ⑤ 선호 조건

필수 조건은 **전부 일치해야 통과**한다. 부분 일치를 허용하면 AI가 잘못 뽑은 조건만 느슨해지는 것이 아니라 제대로 뽑힌 조건까지 함께 느슨해지기 때문이다. AI의 과추출 위험은 엔진을 완화해서가 아니라, **CA가 고객과 함께 조건을 확인·수정하는 단계**에서 막는다.

## 네 가지 결과

| 결과 | 언제 | 다음 행동 |
| --- | --- | --- |
| **정확한 제품 확인** | 원제품에만 성립하는 조건 + 대기·타 매장 방문 가능 | 타 매장 확인 요청 |
| **비교 체험 제품** | 실물로 확인하고 싶은 요소가 매장 내 제품에 있음 | 이 제품 확인하기 |
| **오늘 구매 가능** | 당일 구매가 조건 + 확인된 매장 재고 | 이 제품 확인하기 |
| **추가 상담** | 조건이 불분명하거나 확보 경로가 없음 | 조건 다시 확인하기 |

조건을 만족하는 후보가 없으면 **무리해서 추천하지 않고 추가 상담으로 돌린다.** 그것도 하나의 결과다.

재고는 수량이 아니라 **보유 여부**로 판단하고, `confirmed`/`checked_at` 을 함께 저장해 **확인되지 않았거나 오래된 재고는 확정 경로로 쓰지 않는다.**

## 로컬 실행

**필요한 것** — Java 21, MySQL 8.0, OpenAI API 키

```bash
# 1. 데이터베이스
mysql -e "CREATE DATABASE segue CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

# 2. 환경변수
cp .env.example .env    # DB 접속 정보와 OPENAI_API_KEY 를 채운다

# 3. 실행
./mvnw spring-boot:run
```

기동하면 `DataLoader` 가 **실제 MCM 제품 12개와 SKU·속성·재고·테스트 계정을 자동으로 넣는다.** 별도 초기 데이터 작업이 필요 없고, 재기동해도 ID 가 바뀌거나 중복이 생기지 않는다.

```bash
curl http://localhost:8080/api/products
```

`utf8mb4` 로 만들지 않으면 한글 제품명이 깨져 저장되므로 1번을 건너뛰지 말 것.

## 알려진 한계

MVP 범위를 의도적으로 여기까지 잡았다. 다음 단계는 GitHub 이슈(P2)로 정의해 두었다.

- **토큰 기반 인가 미구현.** 로그인은 있지만 세션·토큰을 발급하지 않아 `customerId` 로 조회 경로에 접근할 수 있다. 데이터를 변경하는 경로는 현재 비밀번호 확인으로 막았다. 고객·직원 양쪽 인증 체계를 함께 설계해야 하는 범위라 분리했다.
- **동의 철회 시 데이터 처리.** 철회하면 조회를 즉시 차단하지만 저장된 상담 결과를 파기하지는 않는다. 실제 운영에서는 보관 기간 정책과 동의 이력 감사 로그가 필요하다.
- **`ddl-auto=update` 사용.** 개발 속도를 위한 선택이며, 운영 전환 시 마이그레이션 도구로 교체하는 것이 맞다.
- **AI 응답 시간.** 보충 질문까지 포함하면 7~8초가 걸린다. 스트리밍 응답이나 조건 캐싱으로 체감 시간을 줄일 여지가 있다.
